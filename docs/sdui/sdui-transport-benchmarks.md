# SDUI transport compression benchmarks

## Recommendation

Use separate static and dynamic profiles; there is no universal best codec/level.

- **Public static assets:** gzip 6, Brotli 5, Zstandard 3, choosing the smallest allowed representation when client quality values tie. Precompute once and reuse bytes. These levels balance startup work and retained representation size. Brotli 11 is an explicit offline-build tradeoff, not a per-request default.
- **Explicitly public dynamic responses:** prefer Zstandard 1, then Brotli 1, then gzip 1; encode only the selected codec. Zstandard 1 is a good large-body CPU/size balance in this corpus. Brotli 1 is particularly inexpensive on tiny inputs. Gzip 1 is a broad-compatibility fallback, but fresh-writer overhead means it is not always faster than gzip 6 for tiny inputs.
- **Response eligibility:** 256 input bytes, at least 32 bytes and 5% saved is a reasonable starting policy. It skips the 182-byte form here and rejects every incompressible case. Thresholds are policy choices, not a statistically established optimum. A latency-sensitive service can raise the minimum to 1 KiB.
- **Browser requests:** keep a conservative 1,024-byte minimum, 64-byte minimum savings and 5% minimum savings; use only natively supported encoders and fall back. These Go measurements do not measure browser encoding cost. CompressionStream provides no portable compression-level control; do not present server levels as browser settings.
- **Secrets:** public-only eligibility is a security boundary, independent of speed. Do not enable dynamic compression indiscriminately on authenticated responses containing secrets and attacker-controlled text. Request compression changes bytes, not confidentiality or CSRF requirements.

## Reproduce

From the repository root, using the Go version specified by go.mod:

```sh
go test ./cmd/sdui-transport-bench
go build -o /tmp/sdui-transport-bench ./cmd/sdui-transport-bench
for run in 1 2 3; do
  /tmp/sdui-transport-bench -duration 100ms > results-run${run}.csv 2> results-run${run}.meta.txt
done
```

The command has `-dataset` (substring) and `-profile` (exact name) filters. For example, `-dataset css-large -profile br11 -duration 1s` isolates one tradeoff. Default duration is 50 ms per encode/decode measurement. Duration is a target, not a hard timeout: an expensive operation completes even when it exceeds the target. There are 120 dataset/profile pairs; full 100 ms runs take at least 24 seconds plus setup, validation, and garbage collection.

Profiles: gzip 1/6/9, Brotli 1/4/5/9/11, Zstandard 1/3/7/15. The Go Zstandard library maps numeric levels to speed presets; these are not twelve independent compression engines or a promise of libzstd's exact level behavior. Inspect its current preset mapping before extrapolating to another library.

Checked-in raw CSV files contain exact encoded sizes, all timing samples, and allocations; tables below are summaries, not a replacement for that evidence.

## Method and limitations

- Linux/amd64, Go 1.26.9, AMD EPYC 9V74 CPU model reported by `/proc/cpuinfo`; `GOMAXPROCS=1`. Shared virtualized CPU, no CPU pinning, no network. Library versions are pinned in go.mod/go.sum. Re-run on production hardware before capacity planning.
- Each pair is round-trip verified before measuring. Encoding uses the production `httpencoding.EncodeWithOptions`, including fresh constructor, whole-body encode, finalization, and output allocation. Decoding uses fresh gzip/Brotli/Zstandard decoders, fully materializes output, and includes decoder cleanup. Zstandard concurrency is one.
- Each timed loop runs at least once and repeats until its target duration. The CSV records iteration counts, mean nanoseconds/operation, total allocated bytes/operation, and allocation count/operation. GC runs immediately before each loop; natural GC during the loop is included. A shared output sink prevents dead-code elimination.
- `B/op` is cumulative Go heap allocation, **not peak live memory, retained memory, RSS, or wire bytes**. Input and initial round-trip buffers are outside the timed loop. No pooling is used. Other workloads, streaming, encoder reuse and parallelism can change the ranking substantially.
- No TLS, HTTP headers, HTTP/2 or HTTP/3 framing, proxy behavior, rendering time, browser parser, JavaScript runtime, browser native encoder, network RTT or end-to-end interaction latency is measured. Decode results are Go decoder measurements, not browser decompression timings. This is a codec/whole-buffer benchmark, not a browser compatibility test.
- Gzip/Brotli/Zstandard levels can produce non-monotonic output sizes on a specific small corpus. Never infer that a higher level must produce fewer bytes. Compare the actual representation.

### Operational interpretation

- Static startup cost is the **sum** of creating the retained gzip/Brotli/Zstandard representations for each eligible asset, plus filesystem/metadata work. It is paid once per process/cache profile, not per successful cached response. The single-shot corpus benchmark measures codec work; the separate HTTP mode below measures actual cache preparation with serial encoder reuse. Neither measures total application boot time.
- Retained static compressed storage for the CSS candidate trio is 8,740 + 8,437 + 9,604 = **26,781 bytes**, in addition to the 43,765-byte identity and object overhead. Temporary encoder allocations are much higher than retained output. Peak startup RSS must be measured separately if a deployment has a tight memory limit.
- Cached static responses perform negotiation and write existing bytes. The per-encode times here do **not** apply to every cached request. ETag/304/cache hits can remove body transfer entirely; compression and cache validation solve different costs.
- Dynamic responses pay rendering/buffering and the selected encoder cost on each eligible request. Preference selection avoids paying for three encoders merely to compare sizes. If a candidate fails the savings check, encoding CPU was still spent; the input threshold is the cheap precheck.
- Brotli 11 improves CSS by only 664 bytes over Brotli 5, while greatly increasing encoding cost. Zstandard 7/15 incur roughly 20/50 MiB cumulative allocations per fresh encode here. Do not choose them as defaults from output size alone.
- HTML and form repetition favors strong dictionary matches; CSS and JavaScript show different rankings. The 182-byte form saves bytes, but per-operation work and framing overhead can outweigh the transfer benefit. Every random input expands; retain identity on failed savings checks.
- These results justify conservative defaults, not a universal minimum. Measure production-like public payload distributions, target browsers, concurrency, mobile CPU and actual network latency before changing thresholds or ordering. Compare pooled/streaming implementations separately rather than substituting their results for this whole-buffer path.

## Actual asset-cache startup and cached HTTP primitives

Run this separately in three **fresh command processes**, so the shared `sync.Once` cache starts cold each time:

```sh
go build -o /tmp/sdui-transport-bench ./cmd/sdui-transport-bench
for run in 1 2 3; do
  /tmp/sdui-transport-bench -http -duration 100ms 2> results-http-run${run}.meta.txt
done
```

`-http` runs these primitives **instead of** the codec sweep and writes only stderr metadata; the original CSV schema is unchanged. The default command does not pay full asset-cache initialization cost. This mode measures the actual currently embedded asset set, rather than the frozen codec corpus. Its evidence records an aggregate SHA-256 over sorted asset paths, byte lengths and contents, asset count/bytes, and default static options; intentional application asset edits can change these results.

The cold operation is one `http.NewServeMux` plus `ui.BindAssets` call in a fresh process. It includes all default asset preparation, MIME/ETag work, encoding and handler registration. It is **not whole application or operating-system startup**: Go runtime/package initialization and command startup occur before timing. Warm binding creates another mux and registers cached handlers; it measures real registration work, not just a cache lookup.

Cached GET/304 measurements use `/assets/app.css`, `Accept-Encoding: zstd, br, gzip`, and `httptest.ResponseRecorder`, with no listening socket or browser. Request construction is excluded; each operation includes a new recorder, mux dispatch, negotiation, conditional handling, headers, and copying the encoded body into the recorder. The GET must return 200 and an ETag; the conditional request must return 304 with no body. Dynamic measurements call production `SelectEncoded` with the fast preference profile on the frozen large HTML/form inputs; this includes negotiation, thresholds and one selected encoder, but excludes rendering and HTTP response writing.

The post-cold retained-heap measurement runs GC and reports HeapAlloc minus the pre-cold baseline. It includes the mux/cache and other live Go objects initialized by binding; it is not an isolated cache-size measurement or peak RSS. The large cumulative allocation count during preparation must not be confused with simultaneous memory use.

### After serial encoder reuse during cache preparation

The implementation now creates one lazy encoder per enabled coding for each static cache build, resets it between assets, copies each finished representation to preserve ownership, and closes it when preparation finishes. No shared concurrent encoder or dynamic encoder pool is introduced. This optimization changes construction overhead, not the configured levels or returned bytes. The frozen single-shot codec tables above intentionally still measure fresh encoders.
